# The Designer's Guide to Verilog-AMS — Gnucap Learning Examples

## OTA conductual en Verilog-A

El ejemplo del [OTA conductual](models/ota/README.md) reúne el modelo, su banco en Gnucap y las capturas originales. El amplificador tiene **70 dB** de ganancia en lazo abierto, un polo de **50 kHz** y una salida centrada en **0 V**. El banco ejecuta barridos DC y AC, además de un transitorio al escalón.

Con Gnucap, ModelGen y un compilador C++ disponibles en la terminal:

```bash
make ota
```

Los datos quedan en `models/ota/results/`. Si está instalado Gnuplot, los PDF quedan en `models/ota/plots/`. Los comandos generales `make build`, `make test` y `make plot` también incluyen este ejemplo.

---

This repository is an educational collection of **Verilog-A** and **Verilog-AMS** examples adapted to run with **Gnucap** and **gnucap-modelgen-verilog**.

The examples follow the progression and ideas presented in *The Designer's Guide to Verilog-AMS* by **Kenneth S. Kundert and Olaf Zinke**. The goal of this repository is to provide small, focused examples that can be studied, compiled, simulated, modified, and inspected independently, making it useful for **self-guided learning of analog and mixed-signal modeling**.

This repository is intended as a practical companion to the book, not as a replacement for it. The book provides the language concepts, modeling methodology, and explanations; this repository provides Gnucap-oriented implementations, testbenches, simulation results, and plots that can be explored directly.

## Purpose of the repository

The repository is designed to help users:

- study Verilog-A and Verilog-AMS through small examples;
- follow the examples in approximately the same order as the book;
- compile Verilog-A/AMS models with `gnucap-mg-vams`;
- run each example independently with Gnucap;
- inspect simulation data and generated plots;
- compare the original modeling concepts with the features currently supported by Gnucap/modelgen;
- understand compatibility adaptations used when the original book syntax cannot be executed directly;
- modify parameters and stimuli to experiment with the models independently.

The examples are intentionally separated into small directories so that each one can be studied without first understanding the complete repository.

The numbering follows the Listings in the book. The `common/` directory contains reusable support examples that are not part of the numbered book Listing tree. Currently it contains the shared `clock` example.

## Typical example directory

A normal model directory looks like this:

```text
<model>/
├── <model>.vams
├── <model>_tb.gc
├── <model>.gp
├── build.sh
├── run.sh
├── results/
└── plots/
```

The files have the following roles:

- **`<model>.vams`** — Verilog-A or Verilog-AMS model.
- **`<model>_tb.gc`** — standalone Gnucap testbench.
- **`<model>.gp`** — Gnuplot script used to visualize the simulation results.
- **`build.sh`** — compiles the local `.vams` source into a Gnucap loadable `.so` plugin.
- **`run.sh`** — runs the local testbench and generates its plot.
- **`results/`** — numerical simulation output generated by the testbench.
- **`plots/`** — PDF plots generated by Gnuplot.

Not every executable Listing requires a compiled model. Some Listings are structural or integration examples implemented directly as testbenches. These directories contain `run.sh`, a testbench, and a Gnuplot script, but intentionally do not contain `build.sh` or a local `.vams` model.

Examples of this approach include structural circuits and higher-level integration tests such as the PLL examples in Appendix A.

## Requirements

The examples require:

- **Gnucap**;
- **gnucap-modelgen-verilog** / `gnucap-mg-vams`;
- a C++ compiler such as **g++**;
- **Gnuplot** for generating PDF plots.

The default build scripts expect the Gnucap headers at:

```text
/usr/local/include/gnucap
```

The root Makefile allows the main executable names and paths to be overridden, for example:

```bash
make GNUGCAP_INC=/path/to/gnucap/include build
```

Available variables include:

```text
GNUGCAP_INC
GNUGCAP_VAMS
GNUCAP
GNUPLOT
TIMEOUT
LOG_DIR
```

## Running the complete repository

The root `Makefile` automatically discovers the model build scripts, Gnucap testbenches, and Gnuplot files under:

```text
Chapter03/
Chapter04/
Chapter05/
AppendixA/
```

The shared examples under `common/` are intentionally run independently and are not part of the root book-Listing sweep.

### Build all compiled models

```bash
make build
```

This finds every directory containing `build.sh` and executes that script.

Each local build typically converts a `.vams` file to C++ using `gnucap-mg-vams` and compiles the generated code into a shared object (`.so`) that Gnucap can load.

Build logs are stored under:

```text
logs/root/build/
```

### Run all testbenches

```bash
make test
```

This discovers every `*_tb.gc` file and runs it directly with Gnucap.

Conceptually, each test is executed as:

```bash
gnucap <model>_tb.gc
```

Before a test is executed, previous `.txt` files in that example's `results/` directory are removed so that the output belongs to the current simulation.

Test logs are stored under:

```text
logs/root/test/
```

### Generate all plots

```bash
make plot
```

This executes all discovered `.gp` scripts with Gnuplot.

The generated PDFs are normally written to the local:

```text
plots/
```

directory of each example.

Gnuplot logs are stored under:

```text
logs/root/plot/
```

### Clean generated files

```bash
make clean
```

The clean target removes generated:

- `.so` plugins;
- `.txt` files inside `results/`;
- `.pdf` files inside `plots/`.

## Running one Listing independently

The repository is also designed so that each example can be studied and executed by itself.

For a normal compiled model, enter its directory and run:

```bash
cd Chapter03/Listing01/resistor
./build.sh
./run.sh
```

`build.sh` compiles the model and creates the local `.so` plugin.

`run.sh` then runs the corresponding Gnucap testbench and executes the local Gnuplot script. A typical `run.sh` performs the equivalent of:

```bash
gnucap resistor_tb.gc
gnuplot resistor.gp
```

The generated data can then be inspected in:

```text
results/
```

and the graph in:

```text
plots/
```

### Testbench-only Listings

Some Listings do not require a build step because they directly instantiate models that have already been implemented elsewhere in the repository.

In these directories, simply run:

```bash
./run.sh
```

For example, Chapter 3 Listings 7 and 8 are structural circuit testbenches, while Appendix A Listings 4 and 10 instantiate the previously developed PLL building blocks directly in their testbenches.

This avoids duplicating existing modules and keeps higher-level examples focused on integration.

## Recommended self-study workflow

A useful way to study the repository is:

1. Read the corresponding Listing and explanation in *The Designer's Guide to Verilog-AMS*.
2. Open the matching `ChapterXX/ListingXX/` directory.
3. Inspect the local `.vams` implementation when one exists.
4. Inspect the `*_tb.gc` testbench to understand how the model is stimulated and observed.
5. Run `./build.sh` if the directory contains one.
6. Run `./run.sh`.
7. Inspect the numerical output in `results/`.
8. Inspect the generated PDF in `plots/`.
9. Modify parameters or testbench stimuli and repeat the experiment.

A typical learning flow is therefore:

```text
Book Listing
     |
     v
Verilog-A / Verilog-AMS model
     |
     v
build.sh        (when required)
     |
     v
Gnucap testbench
     |
     v
results/*.txt
     |
     v
Gnuplot
     |
     v
plots/*.pdf
```

## Compatibility with Gnucap

The original examples in the book were written for Verilog-A/Verilog-AMS simulators available at the time of publication. Gnucap and `gnucap-modelgen-verilog` do not yet implement every construct used by those examples.

For that reason, some examples in this repository use compatibility adaptations while preserving the purpose and behavior of the original Listing as closely as possible.

Examples include explicit mixed-signal conversion in testbenches, scalar representations where vector support is unavailable, and alternative implementations for language constructs that are not yet supported by the current Gnucap/modelgen flow.

A successful compilation alone is not considered sufficient verification. The examples are intended to be built, loaded, simulated through their testbench, and checked through the resulting numerical data and plots.

## Educational use

The examples are intentionally small and focused. They are intended to be read, modified, simulated, and compared with the corresponding material in the book.

For a new user, beginning with `Chapter03/Listing01` and progressing in numerical order provides the most direct introduction to analog modeling. `Chapter04` then introduces mixed-signal behavior, while `Chapter05` contains language-oriented examples and `AppendixA` demonstrates practical integration cases.

The objective is not only to provide working source code, but to make each example useful as a compact experiment from which the user can learn how Verilog-A and Verilog-AMS models behave in Gnucap.
